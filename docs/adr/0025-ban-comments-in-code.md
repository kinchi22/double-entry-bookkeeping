# ADR-0025: Ban comments in code

**Status:** Accepted
**Date:** 2026-09-24

## Problem

Agents read the code in this repository far more than people do, and a comment
tells an agent little the code, a test or a document does not. Before this
record about 3,000 comment lines sat in the JavaScript and TypeScript the linter
sees, in roughly 190 of about 215 files. Many restated an ADR, a test name or an
identifier. Many recorded history -- what a file used to do, which ADR changed
it -- which is stale the moment it is written, and which an agent reads as
current.

Nothing stopped a new one. "Comment the why, never the history" is the usual
rule, and no machine can tell a why from a history, so the rule would have been
enforced by review or not at all -- the failure `docs/ARCHITECTURE.md` opens by
naming.

## Decision

Code carries no comments. `repo/no-comments`, in the repository's ESLint plugin,
is on for every file ESLint lints, and reports every comment, JSDoc and JSX
comments included, except a tool directive that states its reason:

- `eslint-disable`, `eslint-disable-next-line`, `eslint-disable-line` and
  `eslint-enable`, each followed by `-- <reason>`;
- `@ts-expect-error -- <reason>`.

A directive with no `-- <reason>` is reported too. Two fixture rows prove the
rule fires: a prose comment, and a directive with no reason. The directives kept
in the repository prove the allowed side, since the lint gate fails if the rule
reports them.

A reason worth keeping is moved before its comment goes, in this order:

1. Already said by an ADR, `docs/ARCHITECTURE.md`, a test name or an identifier:
   deleted.
2. A rule or an invariant: a test, or a test name that states it.
3. An architectural reason: its ADR, or `docs/ARCHITECTURE.md`.
4. A local, operational reason: a better name, or otherwise dropped.

No document is created to hold displaced comments.

A string that is used -- a test name, `describe` text, an error or log message, a
dependency-cruiser `comment:`, a fixture-map exemption reason -- may explain
behaviour and never carries history or an issue number. No gate checks it;
`AGENTS.md` states it and review holds it. An unused explanatory string is
already `@typescript-eslint/no-unused-vars`.

`stryker.config.mjs` carried the one comment that did work, a JSDoc `@type`. It
is `stryker.config.ts` instead, typed with `satisfies` against the options
`Stryker`'s constructor takes. Stryker loads a config it is given by path with
`import()`, and Node strips the types, so no annotation form is allowlisted.

Out of scope: YAML, SQL, CSS, the environment example and npm config, which ESLint
does not read, and Markdown, which is documentation rather than code. The
generated migration SQL keeps the `--> statement-breakpoint` markers drizzle
needs. `next-env.d.ts` is generated by `next build`, with triple-slash references
Next needs, so ESLint ignores it.

## Consequences

The rationale that sat beside a line is gone from it. A reader who wants to know
why a gate is configured the way it is reads the ADR or `docs/ARCHITECTURE.md`,
not the file, and a reason judged local was dropped rather than moved: some of
what a person would once have learned by opening a file is now learned only from
its history. That loss is accepted in exchange for a rule a machine enforces.

ADR-0004 moved the Stryker config from JSON to `.mjs` so that its exclusions
could carry their reasons inline. Those reasons now live in ADR-0004 alone, the
place its rejected alternatives said a reader would not look. The ownership of
the file (`.github/CODEOWNERS`) is what still makes an exclusion visible.

Directives stay possible, and each costs a sentence. A suppression without a
reason fails the gates rather than a review.

The ban does not reach strings, so the same prose can move into a test name or a
message. The line in `AGENTS.md` is the only thing that says it must not carry
history, and review is the only thing that checks it.

## Rejected alternatives

**"Comment the why, never the history," as a written rule.** It is the rule the
repository already had in practice, and 3,000 lines is what it produced. No gate
can check it, so it rots back.

**Allow JSDoc on exported symbols.** It is the form most likely to restate the
signature, and editors show it, so it is also the form most likely to mislead
when it is stale. An exception by syntax would be an exception by volume.

**Allowlist the JSDoc `@type` annotation in the Stryker config.** It would have
been the only comment kept for what it does rather than what it says, and moving
the file to TypeScript types it as well without one.

**Keep comments in the violation fixtures.** Each one repeated its row in
`tools/gates/fixture-map.ts` and `fixtures/README.md`, which already state which
fixture proves which rule.

# ADR-0010: Model a record as a balanced entry of lines

**Status:** Accepted
**Date:** 2026-09-16

## Problem

The brief names the first vertical slice "Create record with the amount(JPY) ->
list records", and the product is double-entry bookkeeping. "Record" carries two
different models. It is either a single signed amount with a date, which is a
cashbook, or a journal entry whose lines name accounts and whose debits equal
its credits, which is a ledger. Nothing in the repository decides which, and
`packages/db/src/schema.ts` is deliberately empty until this decision exists.

The slice is permanent. The brief keeps it as the reference every later feature
imitates, so the shape chosen here is the shape the product keeps, and the cost
of choosing the cashbook is a data migration of every row once the ledger
arrives.

Two existing rules bound the model:

- An amount is a branded integer count of minor units, scale 0, built and
  combined only through `@repo/core/money`, which returns `Result`.
- Dates are stored in UTC as `timestamptz` and converted at display. That rule
  is about instants. The day a transaction is posted is a calendar day, and the
  book is kept in Japan: midnight in JST is 15:00 the previous day in UTC, so a
  posting day held as an instant is off by one for half of every day.

## Decision

A record is an **entry**: a posting of two or more **entry lines** whose debits
balance its credits. The brief's word "record" is retired; `docs/GLOSSARY.md`
carries the names.

**Entry**

| Field       | Type                        | Rule                                  |
| ----------- | --------------------------- | ------------------------------------- |
| `id`        | `EntryId`, uuid v7          | Generated by an injected generator     |
| `entryDate` | calendar day                 | Required. Future days are allowed      |
| `memo`      | text                        | Required. Trimmed, 1 to 200 code points |
| `lines`     | entry lines                  | Two or more                            |
| `createdAt` | instant                      | Server-set, never supplied by a client |

**Entry line**

| Field     | Type                | Rule                                  |
| --------- | ------------------- | ------------------------------------- |
| `account` | account code        | One of the chart below                 |
| `side`    | `debit` or `credit` | Direction. The amount never carries it |
| `amount`  | `Money`             | Greater than zero                      |

**Invariants**, all decided in `domain/` and returned as a `DomainError`: two or
more lines; at least one debit and at least one credit; every amount greater
than zero; the sum of the debit amounts equal to the sum of the credit amounts,
summed through `addMoney` so an unrepresentable total is an error rather than an
approximation. The same account may appear on more than one line.

**Chart of accounts.** A constant in `domain/`, one account per type, each a
lower-case code stored as text: `cash` (asset), `payable` (liability), `capital`
(equity), `sales` (revenue), `expense` (expense). A line naming anything else is
rejected. Accounts as data are ADR-0015, Deferred.

**Storage.** Tables `entries` and `entry_lines`. `entry_date` is a Postgres
`date`, the one column in this repository that is not `timestamptz`, because it
holds a day rather than an instant. `created_at` is `timestamptz`. `amount` is
`bigint`, read by drizzle as a number. The database enforces shape -- types, not
null, the line's foreign key to its entry -- and the domain enforces the rules.
No trigger checks the balance.

**Wire.** `packages/contracts/src/entries.ts` carries `entryDate` as a
`YYYY-MM-DD` string, `createdAt` as an ISO 8601 string, and `amount` through
`moneySchema`. `EntryId` is branded beside its schema, as `id.ts` describes.

**Display.** An amount is rendered as grouped digits with no currency symbol, as
the Money rule states. A day is rendered as it is stored.

## Consequences

A line names its account by code, so adopting ADR-0015 migrates every line from
a code to an account id.

`bigint` read as a number is exact only inside the safe integer range. The
contract and `money()` both refuse anything outside it, so the app cannot write
such a row; a row written by hand around the app can, and it would read back
rounded. The same is true of the balance: SQL will accept an unbalanced entry
written by hand, because the rule lives in the domain, where it is tested, and
stating it twice would mean two places to keep true.

Future days are accepted, so an entry typed as 2126 is stored. Rejecting them
would put a clock and a timezone into the layer that must have one output per
input.

A memo limit counted in code points is a domain rule; the column is `text` and
holds whatever the domain accepted.

`entry_date` makes the Dates row in `docs/ARCHITECTURE.md` two rules: instants
are `timestamptz`, calendar days are `date`. A reader now has to know which kind
a column holds, and the answer is in this record.

## Rejected alternatives

**A single amount with a sign.** It matches the brief's wording most literally
and needs no accounts. It is not double-entry, it cannot answer what an amount
was spent on, and every row would need migrating into lines later. The repository
is named for the model it rejected.

**Exactly two lines.** The Phase 1 form has two either way, so the only
difference is whether the contract and the schema can express three. A payment
split across two expense accounts is ordinary bookkeeping, and under this
alternative it would arrive as a contract change and a migration.

**The direction as the sign of the amount.** Debit and credit would then have
two representations, and `-0` is a value that compares equal to `0` under `===`
and not under `Object.is`, which is what the assertion library uses. `Money`
already special-cases it for that reason. A side field has one representation.

**Accounts as a table, seeded by the first migration.** It removes the later
migration ADR-0015 describes. It also puts seed data in a migration, a second
table and a second repository read into the slice whose job is to be the
smallest complete path through the layers.

**`entry_date` as `timestamptz`.** Consistent with every other timestamp, and
wrong by one day for the timezone this book is kept in.

**`numeric` for the amount.** node-postgres returns it as a string, and the
first arithmetic on it outside the domain is a float again.
